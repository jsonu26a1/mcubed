while looking at redb's source code, I noticed some odd quirks...

the way redb handles things, the data width for key-value-types is always known (from the table definition used to open the table). when a data type is not fixed width (dynamically sized, like String or byte slice), a list is included before the dyn-sized data in the file, containing the end offset of each entry. I take issue with this approach in a couple of ways; 1) this means an extremely long key might need to be stored more than once; in addition to the leaf node, it might be present in one or more branch/internal nodes. (wouldn't it only be at most twice? yes, I believe it would only appear in at most one branch node).

redb also has an unusual "region/paging" system. I can store a 10 MiB key in redb, and the file size becomes over 30 MiB. and I believe that 10 MiB key is being stored *inline* within the tree nodes, meaning there's a lot of copying to be done when a new value is inserted, and the position of that value within a node changes. now, redb does advise using a "side car" file for large values (greater than a few MiB), or else there's a bad performance (see comment in examples/special_values.rs). so it's not like this that massive of an issue; most dyn-sized keys and values will not be that large, maybe around 1 KiB, so having them duplicated or needing to copy them for insertions/removals for isn't a huge deal.

however, that region/paging system means there's a lot of wasted space when dealing with huge keys and values stored in nodes. I did some tests with writing large keys and the resulting file size of the database, and it's quite inefficient. an empty database is always about 1 MiB, and as I said above, a 10 MiB key took up more than 3x the space. while this flexible region allocation system does let them have these very large contiguous chunks that can be filled with values; (now that I think about it...)

so I think for our "BlockTree" implementation, we will handle large keys and values using "pointers"; if the data is fixed-sized, what we store inline in the node is an "address" containing the data; the BlockTree will have a list of BlockIndex's which represent it's "address space" when concatenated together. if the data is dyn-sized, "tagged" pointers will be used; if the data's length is larger than a `block_size`, instead of pointing into the BlockTree's shared "address space", it will be a BlockIndex to a dedicated block which has more information about where to locate the data.

when data is removed from the BlockTree that are allocated in the address space, the freed slots will be tracked so they can be reused, similar to how freed Blocks are tracked by the Emptylist in the RootHeader. if there's a lot of unused slots (a lot of items are removed), the BlockTree can "compact" the address space by reallocating the values and updating the pointers within the nodes, so they're all contiguous again. however, this would require iterating over all the items in the tree.

for "compacting" the RootHeader's EmptyList, I came up with a work around to optimize the process. (it could technically work for compacting a BlockTree's address space, but might not be worth it). when compacting entire file, it would be very expensive to walk every BlockTree in the entire file and then reallocate blocks with high BlockIndex's (to fill "holes" in the EmptyList) so we can truncate the file (reducing it's size). my idea is to have a "block reallocation lookup table" (a special BlockTree that maps from a original BlockIndex to reallocated BlockIndex). every time a block is accessed, it's BlockIndex is first looked up in this tree. if it's not present, the access occurs unchanged. if it is present, the new BlockIndex is accessed instead. during a "quick compaction", instead of walking every BlockTree (and other data structures) so that certain BlockIndex's can be updated/reallocated, the BlockIndex mappings representing a reallocation are written to this "reallocation table". when a new block is allocated that extends the file, the BlockIndex is looked up in the allocation table; if it's present, the existing "reallocated data" is moved to this new block at the end of the file, the entry is removed from the table, and the newly allocated BlockIndex is the block that the data was just moved from.



back to impl "BlockTree", I guess we could use a similar logic to redb, with how data type width is inferred; if a data type has a width >= 8 bytes, then the "address pointer" system will be used; (u64 address). if data type is dyn-sized/variable width, use tagged pointer, with small data fitting in (this could also be u64 address, with highest bit being the tag).

however, this "inferred/implicit typing" means that we: 1) can't read the BlockTree if the key-value-types are unknown, and 2) the user is forced to use the "pointer" abstraction even if they would rather not (for fixed-sized types, dyn-sized would always require pointers). so instead, I will use "explicit typing", where this info is included in the metadata of the tree's root node/header.
