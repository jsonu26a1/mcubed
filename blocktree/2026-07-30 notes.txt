I fixed a bug causing the panic I documented yesterday, then tried the demo with more elements; once the tree got deeper, I found a flaw in the current `remove()` algorithm. currently each time we merge internal nodes, we permanently "lose" a key; the issue is the last edge node never had a key to begin with, so when we naively merge the nodes, the number of keys is 2 less than the number of edges.

we could either traverse down the tree to reach the leaf node, so we can find the key to add after that edge, OR we could modify the design so that internal nodes have that extra, redundant key for the last edge. traversing the tree isn't that bad, since it only scales with the height of the tree, which is O(log(n)). including that extra isn't that bad either, since for large orders (which our blocktree implementation will have), a single additional key would take up hardly any space on a full node. however, it would require rewriting our algorithm for `insert()`. actually, it would greatly complicate it, since we would have to bubble up changes to the last leaf in an edge further up the height of the tree.

so actually, we should just traverse down the tree to resolve the key for the last edge, within `remove()`. if we modified the design of the tree, so internal nodes had this extra key slot for the last edge, we would have to modify `insert()` and still have to traverse up the tree to update this key. so we would be using more space, AND still need traverse the tree upwards on insertion, so there's no upside to including an extra key slot.

hmm, now that I think about it, instead of traversing down the tree to find the leaf's last key, couldn't we check the parent node, what key they have for our node? that would fail if we're the last edge of our parent, or when the leaf is the last leaf in the tree. so traversing down is the best method.
